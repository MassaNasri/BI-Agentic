## Enforced ownership violations

Five concrete notification foreign-table mappings exist (`users`, `workspaces`, `workspace_members`, `subscription_plans`, `workspace_subscriptions`). Separately, nine core Django service configurations share a PostgreSQL credential; this is an access-control violation even where the process has no domain ORM use. ClickHouse and SurrealDB have multiple independent clients using shared credentials. Counts describe different measures and must not be added as if each were a unique SQL path.

## Migration mechanics

First add owner APIs while the existing database remains in place. Replace foreign reads with those APIs and test denial/outage behavior. For each owner's table set, create a private database/role, apply a corrected initial migration graph, copy IDs and sequence positions, reconcile counts/checksums and inspect orphan scalar IDs. During a short write freeze, apply the final delta and switch only that service's connection. Do not keep an unbounded dual-write period. HTTP publication uses idempotency keys and a durable owner-local outbox/job dispatcher; no cross-database transaction is assumed.

Move report/page/widget tables as one unit. Move voice jobs separately after replacing the report foreign key with a scalar report_id and verifying job APIs. Migrate Django history deliberately: do not copy a shared django_migrations table into every new service and pretend its schema exists. Test each owner's migrations against an empty disposable database. Keep the original database read-only until reconciliation and rollback windows close. Rollback before new writes may switch connections; rollback after new writes needs a tested reverse delta and cannot merely select the old DB.
