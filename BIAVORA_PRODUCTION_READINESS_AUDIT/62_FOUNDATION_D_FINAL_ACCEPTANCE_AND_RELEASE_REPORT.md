## Performance Bottleneck Analysis

The baseline showed most elapsed time after raw completion. Source-to-raw was 60.891 seconds; raw-to-Normalizer completion added 1,270.282 seconds; Loader completion followed 161.208 seconds later. The original worker path waited for each downstream send and progress callback and committed per record. Loader also performed one identity lookup and insert per new event. These code-path observations, the stage offsets, and the large post-raw delay motivated bounded batching. Per-stage CPU microbenchmarks and aggregate callback wall time were not independently captured, so no precise CPU attribution is claimed.

## Callback / Checkpoint Profiling

The old worker path could issue a progress callback and Kafka commit for each processed record. The optimized path checkpoints only the safely completed contiguous batch range and commits after the downstream effect and callback. It retains the maximum LSN and generation scope. The final audit observed 5,181 normalized and 5,181 transformed events and no DLQ events. A standalone callback wall-time histogram was not collected.

## Optimization Design

`etl-final/shared/cdc/worker.py` now uses bounded, single-scope partition batches, asynchronous producer sends followed by durability waits, one progress callback through the contiguous end, and one Kafka commit. Producer linger is 5 ms with a 131,072-byte batch buffer. `etl-final/shared/cdc/clickhouse.py` limits bulk application to 100 events, validates each contract, checks full identity/version matches, deduplicates within the batch, and applies safe rows through one JSONEachRow write. The existing one-record path remains available.

## Batch Semantics

No batch mixes pipeline/generation scopes. Output is durable before checkpoint, and checkpoint precedes input commit. A failed callback or input commit leaves replayable input. Snapshot-completion notification still comes from Debezium and is not synthesized by a batch. Bounded memory, ordered offsets, and maximum LSN are asserted in the worker tests.

## Poison / Partial Batch Semantics

The `valid, valid, POISON, valid, valid` test publishes and checkpoints only the safe prefix, records a payload-free DLQ disposition for the poison, pauses the scope, and leaves the later records unacknowledged. A callback failure replays the prefix. The worker does not silently skip over the poison.

## Loader Conflict Semantics

The store distinguishes exact duplicate, new version, and conflicting same-version identity. A conflict in a batch flushes the safe prefix, emits `CDC_VERSION_CONFLICT` for the conflicting event, and leaves later rows pending. Tests cover mixed duplicate/new, delete/update, conflict, and partial insert replay. An uncertain partial ClickHouse insert is rechecked by exact identity on retry; it is not acknowledged as a whole unknown batch.
